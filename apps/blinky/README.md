# Your first XIAO nRF54LM20A V1.0 project

This is a small, complete Zephyr application: blink the blue LED and print its
state every 2.5 seconds (`BLINK_INTERVAL_MS = 2500`). It is the starting point for
learning the build workflow before adding wireless code.

Both regular and debug images have been **compiled successfully** using NCS
v3.4.1 and the pinned Seeed board package. The **debug image has been flashed,
verified, and tested with source-level debugging on the board**. The regular
image has not been flashed; UART output validation is still pending.

## 1. Understand the target

Select:

```text
xiao_nrf54lm20a@1.0.0/nrf54lm20a/cpuapp
```

The parts identify the board, board revision, SoC, and CPU:

| Part | Meaning |
| --- | --- |
| `xiao_nrf54lm20a` | Seeed's board wiring, clocks, LED, UART and power configuration |
| `@1.0.0` | Your confirmed hardware revision |
| `nrf54lm20a` | The Nordic chip |
| `cpuapp` | The Cortex-M33 application core running `main()` |

You do not need to program the RISC-V coprocessor for this example.

## 2. Understand the project files

```text
apps/blinky/
  CMakeLists.txt
  prj.conf
  app.overlay
  src/main.c
  build/              generated by the command-line build
```

| File | What you edit here |
| --- | --- |
| `CMakeLists.txt` | Locate Zephyr, add Seeed's board root, and list application C files |
| `prj.conf` | Enable software features: GPIO and the UART text console |
| `app.overlay` | Override hardware configuration: free the LED pins from PWM and disable V1's unwired native USB |
| `src/main.c` | Initialize the LED, change its state, print a message, and sleep |

The useful distinction is **software features in `prj.conf`, hardware description
in devicetree, and behavior in C**. An overlay is optional in a generic fresh
project; this one needs its V1/GPIO adjustments. Keep generated files under
`build/` out of your source edits.

In `main.c`, `DT_ALIAS(led0)` uses the board's blue LED, P1.23. Its active-low
polarity comes from the board description, and `gpio_pin_set_dt()` applies it
automatically. `k_msleep(BLINK_INTERVAL_MS)` suspends the application thread for
the configured interval, currently 2.5 seconds, while Zephyr can run other work.

Seeed's complete board source is in `third_party/platform-seeedboards/`; its
[pin and source provenance](../../third_party/README.md) is recorded separately.
Application changes belong here, keeping the downloaded board package unchanged.

## 3. Open and configure it in VS Code

You can open the repository root as the VS Code workspace:

```text
/home/skipper/repos/seeed_studio_nRF54LM20A
```

Or open `apps/blinky` directly; it now has equivalent local VS Code settings.
The workspace's `.vscode/settings.json` already adds the Seeed board root. The
application's CMake file also adds it before loading Zephyr. Both refer to the
same pinned source. [Seeed documents the external board-root workflow.](https://wiki.seeedstudio.com/xiao_nrf54lm20a_ncs/)

1. Open the Command Palette and select **nRF Connect: Add Folder as Application**.
   Select `/home/skipper/repos/seeed_studio_nRF54LM20A/apps/blinky`.
2. Under that application, select **Add Build Configuration**.
3. Set the following fields:

   | Field | Value |
   | --- | --- |
   | SDK | NCS v3.4.1 at `/home/skipper/ncs/v3.4.1` |
   | Toolchain | v3.4.1, bundle `8285d8ad56` |
   | Board target | `xiao_nrf54lm20a/nrf54lm20a/cpuapp` |
   | Revision | `1.0.0` |
   | Build directory name | `build-vscode` |
   | Base configuration | `prj.conf` (normally selected automatically) |
   | System build (sysbuild) | **No sysbuild** |

4. Click **Generate and Build**.

Your custom keyboard shortcut **Ctrl+B** runs the default build task (the standard
Ctrl+Shift+B binding is disabled in your user settings). The default is the supplied
**nRF: Build blinky (NCS 3.4.1)** task. This task works from either workspace
folder and launches `west` inside the installed Nordic toolchain. It builds
into `build/`. You can also use **Build** in the nRF Connect sidebar for the
configuration you created there.

To clean compiled outputs, open **Tasks: Run Task** from the Command Palette and
select **nRF: Clean blinky (NCS 3.4.1)**. It runs `west build -d .../build -t clean`
inside the same Nordic toolchain. It removes compiled outputs from `build/` and
keeps the CMake configuration for the next build. This task works when either
the repository root or this application is open as the workspace.

The generic **CMake: build** task is provided by the separate CMake Tools
extension and does not select this project's Nordic SDK/toolchain automatically.
It previously reported `Workspace is ...`, `build failed`, and terminal exit
`-1` before executing a compiler. Use the supplied nRF task or Nordic sidebar
build for this project. Automatic CMake Tools configuration on open is disabled
locally. The supplied task records paths for this machine's installed SDK and
Nordic extension; update those paths if you move the SDK or upgrade the extension.

`build-vscode` gives your UI-created configuration its own directory; the already
verified command-line build remains in `build/`. Both use the same source.
Sysbuild coordinates applications with additional firmware images; a direct
single-image build keeps this first project easier to inspect.

The configure output should identify `Board: xiao_nrf54lm20a, Revision: 1.0.0`
and load this application's `app.overlay`. Successful compilation generates
`zephyr/zephyr.elf` and `zephyr/zephyr.hex` beneath the selected build directory.

If the board does not appear in the picker, verify that the downloaded dependency exists and
**nRF Connect: Board Roots** ends in `platform-seeedboards/zephyr/nrf`. Refresh
the SDKs or reload the window after changing board roots.

## 4. Build the same project from a terminal

Use **nRF Connect: Pick Toolchain and SDK for nRF Connect Terminal** and choose
v3.4.1 for both. Then run:

```bash
cd /home/skipper/ncs/v3.4.1
west build --no-sysbuild -p always \
  -b xiao_nrf54lm20a@1.0.0/nrf54lm20a/cpuapp \
  -s /home/skipper/repos/seeed_studio_nRF54LM20A/apps/blinky \
  -d /home/skipper/repos/seeed_studio_nRF54LM20A/apps/blinky/build
```

`-b` chooses the target, `-s` chooses your source folder, and `-d` chooses generated
output. `-p always` performs a clean configure, useful initially or after changing
boards. Starting inside the SDK workspace lets `west` locate its build command.

For ordinary C edits, the shorter incremental rebuild is:

```bash
west build -d /home/skipper/repos/seeed_studio_nRF54LM20A/apps/blinky/build
```

## 5. Make a small change

Change `BLINK_INTERVAL_MS` in `src/main.c` from its current `2500` to `1000`, then
rebuild. After programming, the expected result is one second on and one second
off.

To try the red LED later, add this alias override to `app.overlay`:

```dts
/ {
	aliases {
		led0 = &red_led;
	};
};
```

The C code still asks for `led0`; the overlay changes which physical LED that
name represents. This is a useful first devicetree exercise.

To start another project, copy `CMakeLists.txt`, `prj.conf`, `app.overlay`, and `src/`
into a sibling folder under `apps/`, change the CMake `project()` name, and create
a fresh build directory. The relative board-root path still works there.

## 6. Programming and observing the board

V1.0's SAMD11 connects USB-C to the Nordic chip's debug and UART interfaces. The
application uses UART20 at 115200 baud for its messages. After programming, expect
the blue LED to blink and a serial monitor to show `LED on` / `LED off` messages.
On this machine the bridge is `/dev/ttyACM0`; its stable device path and the DTR
setting needed for UART forwarding are recorded in [the debug guide](DEBUGGING.md).

Seeed's OpenOCD is now installed locally under the repository's `.tools/openocd/`.
The board's USB CMSIS-DAP probe has been detected. For programming and source-level
debugging, follow [Debug blinky on the board](DEBUGGING.md). Select **Debug XIAO
blinky (build + flash)** in VS Code's Run and Debug view and press F5; it builds,
flashes, and stops at `main()`. Select **Run XIAO blinky (build + flash)** and click
the green triangle to build, flash, and run without pausing. Both operations
replace the application on the Nordic chip.

Hardware validation on October 21, 2026: the prepared udev rule was installed for
Seeed USB ID `2886:0068`, the protected Nordic target was recovered with the
vendor erase/unlock procedure, and `west flash` verified 64,896 bytes of the
debug image. The installed Microsoft C/C++ debug adapter and supplied launch
profile reached `main()` and a source breakpoint, stepped `led_on` from `false`
to `true`, and observed a GPIO result of zero. Breakpoints were then removed,
execution resumed, and the debugger disconnected. A seven-second UART capture at
115200 baud confirmed alternating `LED off` / `LED on` messages afterwards.

Validation recorded: NCS v3.4.1, Seeed commit
`a6fd41debbbcda13b5340fff50c9092ed3289194`, explicit V1.0 application-core target,
all 285 build steps passed. Native USB drivers and MCUboot are disabled; the
generated application starts at offset zero. The build's vendor configuration
emits a non-fatal `NRF_PLATFORM_LUMOS` deprecation warning.
The regular image uses 51,476 bytes of FLASH; the separately built and flashed
debug image uses 64,908 bytes of FLASH.
